# 单服务订单队列

依据本任务已讨论并由用户要求实施的单服务方案 A。直接在当前分支实现，保留用户的设备配置修改。

## 范围

- 新增 services 包，托管 frontend/dist 和同源 API，直接调用 TaskRunner；不再经过前端 Python 代理或旧 Tasks。
- 保持 taskrunner、workflow、commands、robot 等现有后端实现不变，通过动作装饰器记录无库存并在下一单执行前检查可用状态。
- services/catalog.py 集中定义展示商品到 Runner 商品映射；三种饮料直通，六种其他商品映射 water。API 同时返回展示 ID 和 execution_item_id，页面明确展示替代执行。
- 四段进度直接来自四个任务的 TaskStatus；运行时仍可选择商品并加入 FIFO。提供极简等待列表与排队取消、暂停取消回位。
- 单服务维护幂等请求、JSON 持久化历史、runtime_id、状态轮询、库存记录。先持久化受理意图再提交；重启时未完成记录标记结果待核对，绝不自动重放。
- 库存为可用性记录，不是数量。首次未识别标记实际执行商品无库存，所有对应别名同步禁用。暂停不改库存。提供设为待确认的补货入口；模拟场景可配置无货或暂停。
- 致命故障停止接单、取消尚未执行订单，仍可通过 HTTP 查看结果。退出时停止接单，取消等待单/暂停回位，等待活动单结束后关闭资源。
- 真实运行时在 services 中按当前 RobotSetup 命名相机接口组装，两路相机共享给识别/预览；不调用旧完整动作入口，不重复占用相机。
- 同源写请求检查 Origin 和自定义请求头；可选共享访问口令通过 HttpOnly 会话 cookie 登录，真实模式非回环监听要求口令。静态服务仅暴露 dist。

## 迁移

根 launcher.py 启动新服务，原配置和旧历史文件不覆盖。旧前端启动入口跳转统一 launcher，不删除仍被旧测试依赖的兼容代码。文档明确这些兼容入口不再用于新页面。

## 验收

真实 Runner + 假动作覆盖多单 FIFO、请求去重、取消、暂停、缺货别名、重启不重放；HTTP 覆盖静态托管、错误、同源校验及鉴权；页面覆盖四阶段、继续提交、队列取消及刷新恢复。模拟浏览器检查桌面和窄屏。真机不自动启动。
