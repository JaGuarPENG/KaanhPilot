# KaanhPilot 项目发展计划

更新时间：2026-09-16

## 1. 项目目标分层

### 1.1 短期：稳定可重复的机器人服务 Demo

当前重点不是扩展交互形态，而是先发布一个边界清楚、可重复运行的两阶段抓取 Demo，再建立可排队的机器人执行基础。

目标包括：

- 冻结现有两阶段视觉抓取演示流程。
- 将现有物理流程收敛为有名称、有版本的 Workflow；前端入口等待前端方案稳定后再添加。
- 建立机器人任务队列和单一执行 Worker。
- 保持前端变化只影响 `agent_api.py`，不渗透到执行层。
- 为执行成功和失败建立明确结果。

### 1.2 近期扩展：咖啡工作站

咖啡机不能通过网络控制。机器人依靠视觉和物理动作完成取杯、放杯、按键、等待、取杯和运送。

目标包括：

- 完成咖啡工作站现场勘察和动作分解。
- 确定场景基准、杯具、托盘、出液口、按键及状态指示的视觉方案。
- 采用“示教基准位姿 + 视觉偏差修正 + 近距离二次定位”的首版方案。
- 建立独立的咖啡制作 Workflow，不把咖啡机建模为网络设备。
- 为关键物理动作加入动作后验证，禁止不安全的盲目自动重试。

### 1.3 近期基础设施：公司内部仿真与离线调试

目标包括：

- 与机械协作导出并验证机器人 URDF。
- 适配公司内部仿真环境中的机器人状态和运动控制接口。
- 适配仿真 RGB、深度图和点云数据。
- 使相同的 Workflow、Command 和感知逻辑能够在真机和公司仿真模式运行。
- 与公司侧工程师确认模拟相机的通信、数据格式、同步和生命周期接口。

### 1.4 中期：语音和 LLM 交互

现阶段只保留接入边界，不投入主要实现工作。

- 语音或 LLM 未来提交与前端相同的结构化 Workflow Request。
- LLM 只能选择允许的 Workflow，不能直接控制底层 Command。
- 语音、LLM 和多模态 Provider 的具体实现推迟到短期执行基础稳定之后。

### 1.5 长期：受约束的 Agent 化

- Agent 根据目标选择和排列 Workflow。
- Agent 生成的计划必须经过确定性的权限、安全和资源检查。
- 只有在仿真、验证和风险约束完善后，才考虑向 Agent 开放有限的底层 Command。
- 实时控制与安全停止始终由确定性控制层负责。

## 2. 当前实施顺序

### P0：冻结现有演示流程

当前进展：

- `TwoStagePickWorkflow.execute()` 已完成两次视觉定位和抓取动作编排。
- `two_stage_pick.py` 已通过 Workflow 执行真实抓取，并已完成初步真机验证。
- 测试主入口已收敛为 `seven_controller.py` 和 `two_stage_pick.py`。
- 无用 Command 已删除，仍有参考价值的旧功能已移入 `commands/legacy/`。

冻结完成标准：

- 明确一个 `two_stage_pick_v1` 流程及其输入、成功结果和失败结果。
- 当前动作序列由 Workflow 执行，不由测试入口重复编排。
- 固化所用模型、标签、运动参数、标定文件和启动配置。
- 建立最小真机验收清单并连续通过约定次数。
- 删除 `two_stage_pick.py` 中未调用的旧抓取实现。
- 修复 `seven_controller.py` 对旧 `GraspCommand` 名称的引用。
- 检测失败和机器人失败具有明确返回结果。

### P0-R：发布整理与控制器限制说明

发布阻塞项：

- 根目录 README 和运行依赖清单已建立；发布前继续补充启动命令、硬件前置条件和安全说明。
- 决定暂未使用的 `agent_api.py` 是移入 Legacy、删除还是明确标记为未支持。
- 清理引用已删除 Command 或旧类名的代码、测试和注释。
- 移除仓库中的机器地址与登录凭据，改为本地配置或环境变量，并提供示例配置。
- 确认约 92.5 MB 模型权重使用普通 Git、Git LFS 还是独立制品发布。
- 外部发布时补充项目许可证、模型许可证和第三方依赖说明。

本次发布必须明确记录但可以分阶段修复的控制器限制：

- follower 当前只按模型 0 的兼容 TCP 工作，尚未支持左右七轴臂的显式模型选择。
- follower 的起始位姿、目标位姿、UDP 数据和运行状态尚未按模型隔离。
- `mvl` 当前依赖控制器加载与现有多模型变量和布局匹配的工程，不是独立通用接口。
- 在修复前，README 必须写明所需控制器工程、模型顺序和支持范围。

后续控制器适配完成标准：

- follower API 显式接收并校验 `model_id`，能正确读取对应七轴臂状态和发送对应目标。
- 明确双臂 follower 是否互斥或允许并发，并建立资源占用规则。
- `mvl` 所需的七段目标、控制器变量和已加载工程前置条件形成稳定协议。
- 控制器工程或变量不满足要求时，在发送运动指令前给出明确错误。

### P1：建立机器人任务队列

完成标准：

- 使用单一 Worker 串行执行物理任务。
- 支持提交、查询和取消尚未执行的任务。
- 支持来源、Workflow 名称、Workflow 版本、参数和幂等标识。
- 队列和任务状态只服务于当前进程生命周期，不恢复重启前的排队任务，也不提供历史任务查询。
- `agent_api.py` 只负责适配前端请求和响应。

### P2：公司仿真环境适配

完成标准：

- 机器人公共契约不包含真机登录、手动使能等专有操作。
- 仿真机器人能够提供与真机等价的关节状态和 TCP 状态。
- 仿真相机输出符合项目 RGB-D 数据契约。
- 运行配置可以选择 `real` 或 `simulation`，Workflow 和感知逻辑不包含环境判断。
- URDF 中的关节顺序、坐标系、TCP 和相机安装坐标系均有验证记录。

模拟相机接入前需要与公司侧工程师确认：

- 使用 ROS 2、SDK、网络接口还是共享内存通信。
- RGB 与深度是主动拉取、订阅推送还是读取最新帧。
- RGB、深度、点云、内参和外参的数据格式。
- RGB 与深度的时间同步、像素对齐和帧编号方式。
- 深度含义、单位、无效值及相机光学坐标系方向。
- 点云由仿真侧直接提供，还是由本项目根据深度和内参生成。
- 相机启动、停止、断连和仿真重置时的生命周期行为。

### P3：咖啡工作站稳定实现

建议先完成场景与风险调研，再冻结 Workflow。

候选流程：

1. 导航到咖啡工作站。
2. 定位场景基准。
3. 定位并抓取空杯。
4. 定位托盘和出液口并放杯。
5. 定位饮品按键和面板法向。
6. 以受限速度和行程按压按键。
7. 通过视觉确认机器开始工作。
8. 等待并确认制作完成。
9. 重新定位、抓取热饮并运送。

关键原则：

- 固定场景优先采用示教位姿和视觉修正，不追求首版完全泛化。
- 如果允许，优先使用 AprilTag 或 ArUco 建立稳定场景基准。
- 按键定位需要三维位置和面板法向，不能只使用检测框中心。
- 重复按键、重复抓杯等有副作用的步骤不得无条件自动重试。
- 热饮抓取、运送和异常停止需要单独制定安全验收标准。

## 3. 可以并行推进的工作

- 软件侧冻结 Demo 和实现 Task Service 时，机械侧可整理 URDF 所需数据。
- 等待仿真接口资料时，先冻结项目侧 `Camera` 和 `AlignedRGBDObservation` 接口要求。
- 等待咖啡机完整动作设计时，可先采集不同光照、按钮状态、杯子位置的 RGB-D 数据。
- Workflow 和任务队列稳定后，再将咖啡流程接入统一执行链。

## 4. 暂不进入当前实现范围

- 语音唤醒、STT、TTS 的迁移。
- 多 LLM Provider 和多模态实时会话。
- Agent 自主编排底层 Command。
- 多机器人并行调度。
- 为单机器人 Demo 引入 Redis、RabbitMQ 等外部队列基础设施。

## 5. 待确认事项

### 咖啡工作站

- 咖啡机型号、按钮布局和机器固定方式。
- 是否允许粘贴视觉标记。
- 杯子来源、摆放方式、材质和允许的抓取区域。
- 咖啡机开始、制作中和完成分别有什么可观察信号。
- 机器人是否能读取关节电流、力矩或末端力传感器数据。
- 热饮运送允许的速度、姿态和安全距离。

### 公司仿真环境

- 仿真平台及版本。
- 接口形式：ROS 2、SDK、网络协议或其他方式。
- 相机能否直接输出 RGB、深度、分割标签和相机内参。
- 深度含义、单位、坐标系和时间同步方式。
- 是否支持接触、碰撞、夹爪和按键物理仿真。
- 仿真场景资产和咖啡机模型由谁提供。

### URDF

- 完整关节树、关节轴、零位、限位和控制器关节顺序。
- 视觉网格和简化碰撞网格。
- TCP、夹爪、头部相机和眼在手上相机坐标系。
- 仿真关节名称与真机 `model_id`、控制器索引之间的映射。
