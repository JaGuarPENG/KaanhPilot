# KaanhPilot 程序架构

更新时间：2026-09-16

## 1. 架构目标

- 前端协议变化只影响前端适配层。
- 前端、未来语音、未来 Agent 共用同一个任务提交入口。
- 物理任务排队和执行不依赖任何一种交互入口。
- Workflow 在真机和公司仿真模式中尽量复用。
- 厂商 SDK、网络协议和仿真接口不进入 Workflow 与业务逻辑。
- 非确定性的决策层不能绕过安全边界直接控制物理设备。

## 2. 程序分层

```text
┌─────────────────────────────────────────────┐
│ 交互适配层                                  │
│ agent_api / 未来 Voice / 未来 Agent / CLI   │
└──────────────────────┬──────────────────────┘
                       │ Workflow Request
┌──────────────────────▼──────────────────────┐
│ 应用执行层                                  │
│ Task Service / FIFO 队列 / 单一 Worker        │
└──────────────────────┬──────────────────────┘
                       │ 选择已注册 Workflow
┌──────────────────────▼──────────────────────┐
│ Workflow 层                                 │
│ 商品取送 / 咖啡制作 / 未来组合能力           │
└──────────────────────┬──────────────────────┘
                       │ 编排受控 Command
┌──────────────────────▼──────────────────────┐
│ Command 层                                  │
│ 运动 / 抓取 / 拍照定位 / 导航 / 状态验证     │
└──────────────────────┬──────────────────────┘
                       │ 只依赖公共契约
┌──────────────────────▼──────────────────────┐
│ 设备与感知契约层                            │
│ Robot / Camera / AGV / Observation / State  │
└──────────────────────┬──────────────────────┘
                       │ 适配具体运行环境
┌──────────────────────▼──────────────────────┐
│ 基础设施适配层                              │
│ 真机 Backend / 公司仿真 Backend             │
└──────────────────────┬──────────────────────┘
                       │
┌──────────────────────▼──────────────────────┐
│ 外部环境                                    │
│ 机器人 / AGV / RGB-D 相机 / 公司仿真        │
└─────────────────────────────────────────────┘
```

依赖只能从上向下。基础设施适配器实现公共契约，Workflow 不允许导入具体厂商 SDK 或仿真 SDK。

## 3. 各层职责

### 3.1 交互适配层

职责：

- 接收外部协议。
- 做身份验证、字段解析和响应格式转换。
- 将外部请求转换为统一的 Workflow Request。
- 查询任务状态并映射为调用方需要的格式。

不负责：

- 初始化机器人和相机。
- 编排机器人动作。
- 自己维护执行线程或设备锁。

当前前端入口尚未冻结；现有 `agent_api.py` 是旧原型，不属于当前受支持主链路。前端定稿后只在本层建立薄适配器。

### 3.2 应用执行层

Task Service 是所有交互入口共享的应用边界，负责：

- Workflow Request 校验。
- 幂等检查。
- FIFO 排队和单 Worker 执行。
- 维护当前进程生命周期内的任务状态、进度、结果和错误。
- 取消尚未执行的任务。

首版队列不做持久化，不恢复重启前的排队任务，也不保存历史任务。Task Service
采用进程内组件还是本机独立进程，在 P1 实现设计中确定；两种形式都不需要外部消息队列。

推荐内部请求字段：

```json
{
  "idempotency_key": "request-id",
  "source": "frontend",
  "workflow": "demo_pick_delivery",
  "workflow_version": 1,
  "arguments": {
    "item_id": "water"
  }
}
```

### 3.3 Workflow 层

Workflow 对应完整业务能力，负责：

- 校验业务级前置条件。
- 按顺序调用 Command。
- 发布阶段进度。
- 在允许的位置响应取消请求。
- 执行动作后的结果验证。
- 对无法确认结果的物理动作返回明确错误，不自动重试带物理副作用的动作。

Workflow 不解析前端 JSON，不直接操作任务队列，不依赖真实或仿真厂商 API。

当前需要优先稳定：

- `demo_pick_delivery@v1`
- `prepare_coffee@v1`（完成场景调研后建立）

### 3.4 Command 层

Command 是可测试的受控设备操作，例如：

- 移动到初始位姿。
- 沿工具坐标系偏移。
- 抓取或释放。
- 获取一次新鲜 RGB-D 观测。
- 定位目标操作位姿。
- 导航到工作站。

Command 应声明参数范围、超时、前置状态和失败语义。带物理副作用的 Command 不能因网络超时而默认自动重试。

### 3.5 设备与感知契约层

相机侧已经具备公共 `Camera` 接口和 `AlignedRGBDObservation` 数据契约，可直接用于真机和公司模拟相机适配。

机器人侧需要补充最小公共契约，至少覆盖：

- 生命周期和连接状态。
- 读取关节与 TCP 状态。
- 关节运动和笛卡尔运动。
- 夹爪动作。
- 停止和资源关闭。

真机登录、手动使能、WebSocket 命令格式等属于真实机器人适配器，不属于公共契约。

### 3.6 基础设施适配层

目标适配器包括：

- `KaanhRobotBackend`：真实机器人。
- `OrbbecG305Camera`：真实 RGB-D 相机。
- `CompanySimRobotBackend`：公司仿真机器人。
- `CompanySimCamera`：公司仿真相机。

具体类名可以在实现时调整，但职责边界保持不变。

## 4. 运行模式

系统应通过组合根或工厂选择运行环境，而不是在 Workflow 中写条件分支。

```text
real        → 真机器人 + 真相机 + 真 AGV
simulation  → 仿真机器人 + 仿真相机 + 仿真场景
```

禁止在 Workflow 中出现类似以下逻辑：

```python
if simulation:
    ...
else:
    ...
```

差异应由适配器处理。

## 5. 相机和仿真数据契约

所有相机适配器应输出同一种 RGB-D 观测：

- `rgb`：`uint8`、`H x W x 3`、RGB 通道顺序。
- `depth_m`：`float32`、`H x W`、单位为米，并与 RGB 对齐。
- `point_cloud_m`：`float32`、`H x W x 3` 的有组织点云。
- 点云坐标系：相机光学坐标系，X 向右、Y 向下、Z 向前。
- 无效深度和点云坐标使用 `NaN`。
- 观测包含帧编号、采集时间、Profile、内参、畸变和对齐信息。

如果仿真环境只提供深度图，适配器负责利用相机内参生成点云。Workflow 和感知算法不能感知这个差异。

## 6. 咖啡工作站架构

咖啡机属于被操作场景，不是可通信设备，因此不存在 `CoffeeMachineBackend`。

```text
PrepareCoffeeWorkflow
    ├── 导航 Command
    ├── 场景基准定位 Command
    ├── 杯子操作位姿估计 Command
    ├── 抓取与放置 Command
    ├── 按键操作位姿估计 Command
    ├── 受限按压 Command
    └── 视觉状态验证 Command
```

首版视觉策略：

1. 使用固定示教位姿到达工作区域。
2. 通过标记或稳定视觉特征确定咖啡工作站坐标系。
3. 从工作站坐标系计算杯架、托盘、出液口和按钮粗略位置。
4. 接近后使用眼在手上 RGB-D 相机二次定位。
5. 从点云估计三维位置和操作表面法向。
6. 执行动作后通过独立视觉观测验证状态。

按键目标应使用操作位姿而不是普通目标点，至少包含位置、朝向或表面法向、置信度、观测帧和时间。

## 7. 未来语音、LLM 和 Agent 的预留边界

当前只固定以下接口原则：

- 语音和 LLM 是新的交互适配器，不是新的执行引擎。
- LLM 只能产生结构化 Workflow Request。
- Workflow Registry 是 LLM 可调用能力的允许列表。
- Task Service 继续负责幂等、排队和状态管理。
- Agent 的规划结果必须经过确定性校验后才能执行。

当前不需要实现语音管线、模型 Provider 或多模态会话。

## 8. 当前代码与目标结构的主要差距

- 当前受支持入口为 `seven_controller.py` 和 `two_stage_pick.py`，前端适配器待后续重新接入。
- 当前任务管理是“忙时拒绝”，还不是 FIFO 队列。
- `TwoStagePickWorkflow.execute()` 已接入 `two_stage_pick.py` 并完成初步真机验证，但入口文件仍保留重复旧实现。
- Workflow 和 Command 的类型仍较多依赖具体 `KaanhRobotBackend`。
- follower 尚未完成多模型双七轴适配，当前兼容 TCP 默认指向模型 0。
- `mvl` 尚依赖控制器加载与当前多模型变量匹配的工程。
- 相机公共契约已经形成，是仿真适配可以直接复用的基础。
- 公司模拟相机的通信形式和数据交付方式仍需与公司侧工程师确认。

## 9. 依赖规则检查表

新增代码时应检查：

- 前端字段名是否进入了 Workflow？如果是，应移回适配层。
- Workflow 是否导入了厂商或仿真 SDK？如果是，应新增适配器。
- LLM 是否能指定任意函数或 Command？如果是，应改为 Workflow Registry。
- 物理动作是否因超时被自动重试？如果是，应重新定义失败语义。
- 仿真分支是否散落在 Workflow？如果是，应移入运行环境工厂或适配器。
- 感知代码是否假设真机相机对象？如果是，应只依赖公共 RGB-D 观测。
